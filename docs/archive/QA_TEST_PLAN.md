## 1. 工作目標與交付界線

這次工作的目標是讓使用者能正確操作、理解結果與恢復錯誤，也讓評審能檢查資料來源、方法合理性、應用價值與可重現性。不能只以「畫面能開啟」或「單元測試通過」作為完成依據。

本文件是後續修改與完整驗收的執行規劃。已完成的基線檢查、程式碼發現與待執行測試分開記錄；本文件列出的修正不代表已完成。完成執行後，必須另交付測試報告與問題修正紀錄。

「確認沒問題」的操作定義：下列指定範圍完成測試，沒有未處理的 P0／P1 問題，所有已修正問題有回歸證據，保留限制能在畫面及報告中清楚辨認。這不代表可保證軟體永遠沒有缺陷，也不代表已證明推薦能提高實際比賽勝率。

本次涵蓋：

- 新增配球比較的 Python 計算、資料清理、API、靜態快照及前端呈現。
- 與新增功能相接的代打、換投、候選列選擇、左右打、模式切換和歷史回放。
- 搜尋／勾選名單、輸入驗證、載入錯誤、快速切換、鍵盤及手機操作。
- 原有推薦結果的回歸檢查，確保介面修改沒有改變模型輸入或排序。
- 展示與答辯中涉及的數據正確性、研究引用範圍、應用創新主張。

模型本身的預測效能、2026 資料完整度、真實教練研究與公開網站競品盤點，必須另有證據才可宣稱完成。推送、部署或對外發布不是本文件的測試前提。

## 3. 已發現的問題與修正優先順序

以下根據目前程式碼檢查整理。正常使用問題先以 UI 重現；失敗分支與競態問題以受控條件注入重現，不能把潛在分支誤寫成每次使用都會發生。

嚴重程度：

- **P0：結果可信度受損。** 錯誤投手／日期結果、使用未來資料、錯誤的數值或分母。必須修復才能驗收。

- **P3：輕微呈現問題。** 不影響結果與主要任務的排版或文案。

## 5. 測試環境、資料與固定情境

### 5.1 測試模式

1. **Python 核心模式：** 直接呼叫 `compare`，使用可手算人工資料與真實逐球資料。
2. **本機完整模式：** 以正常 `python server.py` 啟動，測試原模型、評估、新 API 與歷史回放；不得僅啟動 Handler 就宣稱完整啟動通過。
3. **本機靜態模式：** 以 HTTP 提供 `docs/`，模擬 GitHub Pages 的純靜態計算、回放與配球快照。
4. **部署模式：** 若有經授權部署的此次修改版再測。原 GitHub Pages 尚未包含本地修改，不能以原站結果當成新功能已部署的證據。

同一固定情境在模式 2、3 比較。既有模型及守位資料版本需相同；若一邊缺 2025 守位資料，先記錄差異，不能把來源不同造成的結果硬判為介面錯誤。

### 5.2 固定資料集合

| 集合 | 選取原則 | 用途 |
|---|---|---|
| A 可比較先發 | 使用鋼龍等實際符合門檻的快照；每次記錄截止日及 hand | 完整比例、差異與區間呈現 |
| B 小樣本後援 | 林子昱等實際不足的情境；不可只看名字就假定不足 | 不足原因、有效場數與低涵蓋率 |
| C 無歷史 | 球季開始前，或投手首場當天 | 缺值、空窗口及日期排除 |
| D 季中／季末 | 4 月、6 月、9 月各取實際回放打席，記錄 pa_id | 時間安全與月份模型區別 |
| E 數學資料 | 組成反轉、+13 pp、單球種、稀有球種、缺條件 | 可手算統計 oracle |
| F 品質異常 | 不明球種／左右打、缺座標、非法球數、投手歸屬不一致 | 清理分母與排除可追溯性 |
| G 故障資料 | 缺明細、404、500、非法 JSON、慢回應、版本不符 | 錯誤恢復及競態 |

建立 `tests/fixtures/qa_scenarios.json`，固定球隊、投打者、守位、板凳、牛棚、日期、比分、局數、出局與壘包。不能只記「選一位投手」而缺少重現條件。

故障檔放在測試 fixture 或隔離測試目錄，以可恢復方式模擬；不可直接損壞唯一的正式資料。

### 5.3 平台矩陣

首要矩陣：1280×800 桌面、1024×768 邊界、768×1024 平板、390×844 與 360×800 手機、320 px 窄畫面壓力測試，另以桌面 200% 縮放檢查。

Chrome 與 Edge 至少各驗證一次關鍵旅程；手機 Safari／Chrome 若未具備真實裝置，標為待外部驗證。調整桌面視窗為手機寬度只能驗證響應佈局，不等於真實手機瀏覽器已通過。

明暗模式分開記錄。自動化可檢查可及性屬性，真正螢幕閱讀器朗讀結果需以該工具實測。

### 6.1 真正使用者研究的安排

先完成上述模擬操作，再邀請 5–8 位便利取樣參與者，包含熟悉棒球的使用者與不熟悉統計的使用者；若能邀請教練／分析者則單獨記錄背景。不把這種小樣本便利取樣當成普遍代表性證據。

不先解說方法，給任務：「選一組投打、找出近期變化、說明能否採信、解釋不足原因」。記錄任務成功、耗時、協助次數、錯誤點、使用者原話與理解題答案。協助後完成與自行完成分開。

規劃性目標：關鍵任務成功率至少 90%；截止日、百分點、小樣本與「使用比例不等於效果」等理解題至少 80% 正確。樣本太小時同時報告人數，如 4/5，而非只報百分比。這些是產品驗收目標，不是研究證明的標準。

有誤解就修文案／版面再以同等任務複測；不要只要求參與者多讀文件。

### 7.1 建議展示順序

1. 展示對決評估，並說明新增功能解決全季分佈看不出近期調整的問題。
2. 展開符合門檻的真實案例，指出日期、窗口、原始比例與調整後差異。
3. 用手算案例解釋為什麼控制球數與左右打。
4. 展示小樣本案例，說明何時不能作判斷。
5. 展示季中歷史情境，指出僅使用實際比賽日期以前的數據。
6. 展示來源、測試證據及未控制因素；解釋為何目前未把變化直接加進推薦分數。

先讓功能和限制可見，再解釋算法。正常案例與限制案例都應出現，不能只選特別漂亮的結果。

### 8.2 全量靜態掃描

掃描 `docs/data/pitch-change/2025/` 索引中的全部167位投手與全部快照、三種hand：

- 索引文件都存在、可解析，schema一致；哈希鍵不衝突，沒有指向索引外路徑。
- `effective_from` 嚴格遞增；同日僅一個日期狀態；每個hand都存在。
- 回傳投手、球季、左右打與文件身份一致；最後觀察日小於截止日。
- 所選比賽都小於截止日，不跨季；窗口互斥、球數非負、有效場不多於所選場。
- 有觀察時原始比例四類合計=1；有支持時調整後比例合計=1、權重合計=1；沒有支持則為缺值。
- 覆蓋率、原始及調整後比例在0–1；差異在−100至100 pp；區間端點有序、有限，範圍合理。
- ready必須滿足所有質量門檻；insufficient必須附不足理由；不得出現狀態與數字門檻矛盾。
- 區間、有效重抽樣次數與解釋標籤相容。

以上全量結構掃描應輕量，不必全部重訓。統計重新計算另分為：全部最終快照重新計算、每位投手至少首／中／末快照重新計算，以及所有曾失敗的快照。資源許可時，再執行全部快照與Python重新計算的全量比對，明確記錄實際完成範圍。

### 8.3 靜態／API一致性

在有新出賽的日期、當天截止、隔天生效、兩場之間的空日期、季末之後的截止，以及三種hand進行比較。靜態選擇器保留用戶查詢cutoff，而狀態來自最新有效快照；因此比較時不能誤把快照原生成截止日與查詢截止日差異判為數值錯配。

數值容許絕對誤差≤1e-10；JSON身份、比賽列表、狀態、理由、設置及缺值語意完全一致。順序相關字段按契約比較，排除理由對象可按鍵比較。

## 9. API、故障恢復與競態測試

## 10. UI、可及性與信息理解

繼續使用 ui-ux-pro-max 作審查，重點採用適用於原生Web的鍵盤導航、表格處理、錯誤恢復與信息提示建議。不新增框架作為解決問題的前提。

檢查項目：

- 每個輸入有可關聯的標籤；同名的「全選／清除」能辨識所屬板凳或牛棚。
- 代打、牛棚、比賽、打席選擇有原生按鈕或等價鍵盤行為；不能只用click的div。
- 新卡控制、主要操作與替代壘包操作提供可用觸控目標；保留圖形顯示時也有鍵盤等價入口。
- 焦點清楚，不被固定header遮住；異步更新不將使用者正在操作的焦點無故丟失。
- 加載、錯誤、不足狀態可被朗讀；大量表格內容不要每次全部塞進live區域重複播報。
- 一般文字實際對比達到4.5:1；大字與關鍵非文字控件依適用標準檢查；顏色不是區分基準／近期或成功／不足的唯一手段。
- 驗證percent、pp與區間的意思：10%→15%是增加5個百分點，不是增加5%相對量。
- 四捨五入邊界、真實0、沒有觀察與沒有區間互相區分。
- 「有效場」「有效球」「共同條件涵蓋率」在同一屏幕可理解；低覆蓋時不能只看到大幅差異。
- 「低落」提供球種說明，不讓使用者以為是投球高度。
- 歷史模型截止與新卡實際比賽截止分別標示，不能造成兩者使用相同訓練窗口的誤解。
- 200%縮放不截斷關鍵按鈕、姓名、比例、錯誤及日期；觸控使用不依賴hover才能瞭解關鍵信息。
- 原推薦的分數、相對勝率說明、誤差與價值排名不因新卡而被重新解釋成比賽絕對勝率。

若新增說明，應放在真正會誤讀的位置，文字簡短；不要用大量警告淹沒有效結果。

## 11. 性能、重複性與更新流程

### 11.1 性能測量

記錄資料總大小、索引大小、投手文件中位數／最大值、解壓後體積、首次請求與緩存請求延遲、讀取與渲染時間，以及本機初次模型加載時間。

建議內部目標：

- 默認收合時不下載投手快照文件。
- 已緩存投手的hand切換在可見操作後快速更新，目標≤300ms；實際機器與測量方式必須記錄。
- 本機新API熱緩存目標p95≤500ms；冷讀取單獨記錄。
- 使用明確模擬的10Mbps與100ms往返網絡條件，新卡首次可用目標≤3秒；不把不同網絡下的失敗混算。
- 連續切換多個投手不出現持續內存增長、長期UI卡頓或失控併發。

這些是測試預算目標，不是已測得結果。不因未達某個目標就立即重寫架構：先找出是首次讀取、JSON體積、渲染還是模型訓練。

### 11.2 更新與緩存

以相同源資料重新匯出兩次，比較所有JSON內容與索引，確認可重複。修改一場測試資料後匯出，確認只有相關狀態改變，舊截止日前結果不變。

本機observations與API存在快取，重啟後才取得新資料；報告要記錄這一點。靜態瀏覽器緩存也需驗證重新發布後不會混用舊schema或舊索引與新文件。若加版本號／緩存策略，應以真實更新測試證明作用。

匯出中斷時驗證不能讓新索引指向未完成文件；優先考慮臨時文件、成功後替換與驗證清單。不要用遞歸刪除目錄來處理尚未確定的舊文件問題。

## 12. 原功能回歸與變更控制

固定輸入保存修改前的：情境、候選集合、排序、球員／投手分數、預估勝率、相對現任值、誤差、守位說明及疲勞調整。修改後數值應保持一致，除非對應明確已證實的舊錯誤。

修復搜索導致選人變化時，正確方式是給模型提交預期的同一名單，再比較結果；不能拿名單已經不同的前後輸出宣稱模型回歸失敗。

對完整輸出比較：輸入模型版本與資料一致時，數值絕對誤差容許≤1e-10；不能用「推薦大致一樣」代替候選與數值檢查。既有靜態與Python模型導出可能有其原誤差契約，應單獨依該契約檢驗，不能混作新功能精度。

每項修正：重現案例失敗→最小修改→該案例通過→受影響的核心／API／UI回歸→問題關閉。新的源碼、設置或資料改變後，重新執行受影響範圍；沒有變化且已通過的昂貴模型訓練不需盲目重複。
