## 2. 正式載入器改用穩定身份鍵，名稱只作呈現

主要範圍：`src/load.py`、`src/identity.py`，以及所有使用 load() 結果的消費端。

1. 建立從已驗收 SQLite／同一來源解析邏輯到正式 DataFrame 的明確介面；一份資料決定打席、逐球、球速與名單，不讓不同路徑各自按姓名拼接。
2. 模型內部、字典、群組、合併與快取使用來源命名 ID；另保留原始姓名、顯示姓名、觀測日期、隊伍及來源位置。不能把「新增 ID 欄，但內部仍按姓名 groupby」當作完成。
3. 打席統計採打席參與者，逐球統計採事件參與者；保留原始 PA ID、PITCH 序號 j 與 event_index，避免球速及標籤錯位。事件缺少欄位與明示空值分開處理。
4. 六組改名共用同一身份歷史，同名林子崴兩人保持不同鍵。移除僅適用單一同名案例的特殊內部姓名鍵，呈現仍可帶必要的辨識資訊。
5. 歷史名稱和隊伍只從截止日前證據取得；訓練沿用嚴格 `< cutoff`，身份查詢的 `--as-of` 則維持明確的日期包含語意，兩者不能混用。
6. 檢查逐球換人後的投打慣用手：不能沿用打席摘要中另一位球員的 bhand/phand。優先使用同一球員在允許日期內可追溯的手別證據，區分左右開弓與當次站位；證據不足時依預先定義的缺值路徑處理，不能直接猜右投／右打。先產出受影響球與可解決／未解決數量。
7. 檢查球數、最後一球、擊球強度、得分價值與換人前後事件的關係；不得把最終打席結果、終局投手用球數或最後打者資訊錯歸給較早參與者。

交付：正式身份介面、全來源映射差異報告、手別證據報告。驗收：720 場全量逐筆對應一致；身份或手別不能解析的樣本都明確計數與處理；無姓名跨人合併、無時間洩漏、無 PA／逐球重複或遺失。

## 3. 名單、守位、疲勞與缺值政策一起接入

主要範圍：`src/roster.py`、`src/fatigue.py`、`src/pitch_change.py`、`src/recent.py`、`src/engine.py`、`server.py`、`src/ml_compare.py`，以及名單／守位匯出工具。

1. CPBL 與 ldkrsi 的來源 ID 保留各自命名空間。建立可稽核的跨來源對照，證據須包含來源 ID、名稱、年度／隊伍等；相同姓名或相同字面 ID 不會自動證明是同一人。
2. 對照分為確認、歧義與無證據。所有未確認的守位連結有明確清單；維持人工確認狀態，不自行認定接守資格。跨年守位整季資料的使用仍遵守原有年份截止限制。
3. 名單、投手／野手分類、候選池、捕手樣本、配球比例、近況統計、疲勞及當場累積用球數都按身份鍵計算；逐球換投情境不把前一位投手的球數算給後一位。
4. 打者改名或轉隊不因舊名字失去可確認的歷史；候選可用性仍依當日證據，不把未出場空檔推成離隊，也不把整季出場名單當成已確認的當日登錄名單。
5. 四筆異常球速轉為有原因的缺值供模型使用，原始檔不改寫；座標、球種、手別等缺值也有一致政策和處理筆數。量測原始檢查未通過與「在明確缺值政策下允許使用」是兩個不同判定。
6. 模型填補值只能由該模型訓練資料計算。特別檢查 `features()` 中球速 fallback，不能用待預測／評估資料本身的平均數補值。

交付：跨來源對照及未解決清單、缺值政策、候選與用球數差異報告。驗收：每個確認的守位關係有來源與日期；歧義不冒充資格；所有填補參數只來自訓練期；數值仍可追溯到球員、事件及政策。

## 4. 建立新模型版本，完整重訓與回測

1. 先完成版本契約設計，再建立與 v4 隔離的新訓練版本，預計 v5；資料 schema、身份介面、訓練版本、engine contract、批次驗證與快取一併更新，不能只改 pkl 檔名。
2. 在新目錄重訓目前網站需要的所有月初模型與完整資料模型。若現行評估仍依賴實驗權重，也須按新資料重建，或明確調整評估流程，不能混用 v4 特徵／舊權重。
3. 先維持現行模型架構、集成權重、校正方法與推薦門檻；將身份與事件修正的影響分離，避免同時調參後無法解釋差異。
4. 對照同一批可觀察打席，檢查 MSE、MAE、均值偏差、分月／分隊／樣本量分組、改名及逐球換人群組，以及候選排序與建議改變的比例與幅度。報告單位清楚，不把誤差改善寫成勝率提升。
5. 重新計算校正參考與所有依賴新身份的基準；RE 與訓練標籤都只使用 cutoff 以前完成的比賽。種子、訓練設定、缺值參數及來源雜湊寫入模型 manifest。
6. 現有 2024–2025 評估資料已被多次檢視，報告只能稱為回溯評估／敏感度檢查。既有月份不得再稱為全新獨立測試集，也不因重切同一批資料就宣稱有新的選模後證據。
7. 先做單月訓練量測，核對當前 CPU／RAM 後再分派互斥工作；限制同時 worker 與每個 worker 執行緒，保留電腦可用性，完成 checkpoint 後可續跑。GPU 是否可用由實際演算法決定。

預先固定的候選發布檢查：資料／身份／截止日／數值單位／版本一致性屬零容忍；模型退化先以整體 MSE 或 MAE 相對惡化超過 1%、任一月份超過 3% 作為必須停下調查的觸發線，而非自動通過規則。觸發時提出誤差、抽樣不確定性、樣本組成及排名變動原因，不為過門檻改回錯誤身份或刪除不利樣本。這組觸發線須在首次候選訓練前記錄凍結；所有未解釋的重大變化都阻止發布。

交付：新模型批次、訓練與校正 manifest、同資料基準比較、樣本與排序變動清單、完整回測。驗收：所有必需截止日模型完成且相容；零時間洩漏；所有重大差異有解釋與處理，沒有因指標不好而掩蓋來源修正。

## 6. 回測與數值呈現完整驗收

1. 針對一般使用者、球隊及單日分析，測換打／換投、名單套用、守位安排、配球樣本不足 fallback、日期切換、上一／下一打席、開啟實際結果及重新載入。
2. 逐球換人情境檢查當前投手、打者、捕手、手別、球數、候選移除、已出場／被換下狀態與勝率局勢是否對得上原始事件；不提前揭露該決策後的結果。
3. 用同一情境逐項核對 Python 與 JavaScript 的分數、樣本數、候選排序、守位狀態、百分比／百分點、正負號、四捨五入與極小值。計算公差與顯示精度先固定，再看結果。
4. 回測維持「局勢 → 可採取行動 → 預測比較 → 查看實際結果」的順序；教練實際行動不當成模型正確答案，未觀察的替代行動不能宣稱已驗證贏球收益。
5. 完整掃描所有匯出 JSON 的 NaN、Infinity、null 語意、樣本數、量尺、上下界、單位及引用檔案。未知與合理的零值分開，不能以 0 隱藏失敗。
6. 自動化測試覆蓋此次變更；跑相關 Python／JS 回歸與同版靜態／HTTP 驗收，產物在隔離目錄，避免覆蓋原未提交 QA 檔。
7. 真實瀏覽器測試桌面與窄手機寬度（包含 320／390px），檢查選單、觸控目標、鍵盤操作、橫向溢出、載入／失敗提示、localStorage 持久性、控制台錯誤及手機載入量。瀏覽器模擬寬度的結果不得冒充實體 iPhone／Android 驗收。
8. 檢查分頁 title、首頁主標題、現有分享／應用程式名稱欄位及新版文件名稱一致；以完整字串與分隔符規格核對，再在窄螢幕及較大字級下目視確認換行與可讀性。搜尋舊稱後，將每一處分類為「已更新」或「保留的歷史／引用內容」，不能只靠全域取代或零搜尋結果過關。
